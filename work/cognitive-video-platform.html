01The problem

A bounding box is not an answer. Operators need to know what happened, where, when, and why.

Detection gives you geometry: a vehicle, a person, a zone. It does not tell you that a truck has been waiting at dock 3 for eleven minutes, that a vehicle entered a lane against traffic, or that the same activity is repeating across three cameras. Those are temporal and semantic questions.

The obvious answer — run a vision-language model on every frame — is too slow and too expensive. The opposite answer — detection only — cannot interpret behaviour. The system had to be a hybrid, on-prem, and honest about which layer made which decision.

Design target: real-time geometry from YOLO, periodic semantic reasoning from a VLM, and a product layer that makes both inspectable — events, evidence, and a conversation over the history.

02Design

01

Split perception by cost

YOLO runs on every analyzed frame and produces boxes, classes, and tracks. The VLM runs on short multi-frame batches every few seconds, with the detection metadata injected into the prompt. Geometry is cheap and continuous; semantics is expensive and periodic. The scheduler treats them differently.

02

Reason over clips, not frames

A single frame cannot distinguish “person standing” from “person falling.” The analyzer receives a batch of frames with overlap, so it can see motion and change. One clip can produce multiple independent events — an alert and a comment, for example — each with its own tags and evidence.

03

Suppress repetition with embeddings, not string matching

Repeating the same observation every cycle destroys trust. Events are deduplicated by cosine similarity against recent embeddings, with separate windows for comments and alerts. A suppressed event does not move the anchor; only an event that is actually emitted updates the reference. That detail is what prevents a slow drift into silence.

04

Take preview encoding off the GPU

The original pipeline copied every analyzed frame from GPU to CPU, drew boxes, and encoded JPEGs for the browser. That work competed with inference. In inference-only preview mode, the browser plays each source's raw stream over WebRTC and overlays detections from metadata; the GPU stops encoding frames nobody is watching.

05

Make it observable, recoverable, and bilingual

Per-stage telemetry separates decode, inference, JPEG, probe, and publish costs. Engines are cached across boots. Recording uploads are asynchronous. A face detector that has no gallery to match against turns itself off. Operators get a live event log, analytics, a chat over cross-camera history, and English/Arabic output with RTL support.

03Architecture

The GPU sidecar is deliberately separate from the application. It decodes streams, runs detection and tracking, and publishes metadata to Redis. The FastAPI application consumes that metadata, runs the VLM analysis loop, stores events, and streams updates to a React SPA over WebSocket and SSE.

04Performance

Most of the work was not model accuracy. It was finding where the GPU budget actually went — and removing work that did not improve a decision.

The biggest structural win was inference-only preview. Moving preview encoding out of the sidecar raised the stream wall from 32 to 64–72 concurrent streams on the test workstation, with zero publisher drops at the new wall and 61% GPU utilisation at 48 streams. The GPU stopped paying for JPEGs of streams nobody was watching.

  • Engine caching: boot to first frame dropped from 28.5 s to 6.8 s by deserialising the face engine instead of rebuilding it from ONNX every boot.
  • Async recording: the segment-rotation callback went from 1.99 ms to 0.06 ms — about 33× faster — by enqueuing the upload and Redis index instead of doing them inline.
  • Recognition path: face recognition dropped from 30.5 ms to 7.7 ms per frame by embedding an existing crop instead of re-detecting the face.
  • INT8: GPU utilisation fell from 36.0% to 21.5% on the same code and workload; the engine shrank from 39.6 MB to 16.6 MB.
  • Idle models: when the face gallery is empty, the face detector disables itself, reclaiming the 20–51% GPU it was spending to return “unknown.”
The lesson: the binding constraint was not inference. It was decode and preview encoding. The per-stage telemetry paid for itself by disproving the obvious hypothesis.

05What I owned

  • Platform architecture: the FastAPI application, event model, WebSocket contract, and the React integration that turned metadata into a product.
  • VLM loop: multi-frame batching, prompt and event schema, embedding deduplication, cooldowns, and chat over cross-camera history.
  • Performance: inference-only preview, engine caching, async uploads, recognition path, INT8 deployment, and idle-model gating.
  • Measurement: per-stage GPU/CPU telemetry, capacity sweeps, and golden-replay checks that made each optimization provable.
  • Delivery: customer demos and proofs of concept, translating operational questions into pipeline requirements.

06Results

The platform runs on-prem, serves a live multi-camera wall, produces temporal events with evidence, and answers operator questions in English or Arabic. The same engine supports multiple vertical products; a product is a configuration of modules, not a fork of the codebase.

The performance work compounded: a faster boot made demos practical, async recording removed a latency spike from the streaming thread, and inference-only preview changed the capacity ceiling. None of those came from a new model. They came from measuring the system as a system.

07Reflection

The best architectural decision was separating geometry from semantics. Geometry is cheap and continuous; semantics is expensive and periodic. Once that split was explicit, the scheduling, caching, and UI all became simpler.

VLM latency is not the enemy. Unbounded VLM latency is. The system stays responsive because the slow path has a queue, a budget, and a fallback — not because the model is fast.
